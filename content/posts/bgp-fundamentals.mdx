## BGP Is Not Like IGPs

Border Gateway Protocol operates on fundamentally different principles than interior gateway protocols like OSPF or EIGRP. BGP is a path-vector protocol — it does not calculate shortest paths based on metrics like bandwidth or delay. Instead, it selects routes based on a series of attributes and policies applied to paths advertised by neighboring autonomous systems. BGP runs over TCP port 179, which means it inherits TCP's reliability and does not need its own hello or retransmission mechanisms. This also means BGP peering requires full IP reachability between endpoints before the session can establish.

### eBGP vs iBGP

External BGP (eBGP) connects routers in different autonomous systems and is the protocol that makes the internet function. Internal BGP (iBGP) connects routers within the same AS, allowing BGP routes learned from one eBGP peer to be distributed to other BGP speakers inside the AS without exiting it. A critical rule: iBGP routers do not re-advertise routes learned from one iBGP peer to another iBGP peer. This prevents routing loops within the AS but requires either a full mesh of iBGP sessions or the use of route reflectors to scale. In any network with more than three BGP speakers, route reflectors are the standard solution.

## The BGP Path Selection Process

When BGP has multiple paths to the same prefix, it applies a deterministic decision process to select the single best path. The order of preference, from highest to lowest, is: highest local preference (LOCAL_PREF), shortest AS_PATH length, lowest origin code (IGP < EGP < Incomplete), lowest MED (MULTI_EXIT_DISC), prefer eBGP over iBGP, lowest IGP metric to the next hop, and finally lowest router ID as a tiebreaker. In practice, LOCAL_PREF is the primary tool for influencing outbound traffic within an AS, while MED influences inbound traffic from a neighboring AS — though MEDs are only compared between paths from the same neighboring AS by default.

### Configuring a Basic eBGP Peering

A minimal eBGP peering requires four things on each router: the local AS number (`router bgp 65001`), the peer's IP address and remote AS (`neighbor 203.0.113.2 remote-as 65002`), a network statement or redistribution to originate prefixes, and reachability to the peer address. For eBGP, the peer address is typically the directly connected interface address, and BGP's TTL defaults to 1, ensuring the session only establishes with directly adjacent peers. Use `show bgp summary` to verify the session state reaches Established and that prefix counts are incrementing. The `show bgp ipv4 unicast` table shows all received paths with the `>` symbol marking the best path installed in the RIB.

## Route Filtering and Policy

Raw BGP without policy is dangerous in production. At minimum, apply prefix lists or route maps on both inbound and outbound directions for every peer. Inbound filtering prevents accepting unwanted or malicious prefixes — bogon filtering (blocking RFC 1918 and unallocated space) should be applied on all eBGP sessions facing the internet. Outbound filtering ensures you only advertise prefixes you own, preventing accidental route leaks that can cause you to become a transit AS for other networks' traffic. BGP communities are the scalable mechanism for tagging routes with policy metadata: a route tagged with a well-known community like NO_EXPORT will not be advertised to eBGP peers by the receiving router, giving you fine-grained control over route propagation without per-prefix configuration.
